# Project Plan: Sisyphus Agent Worker

## Overview

Create **SisyphusWorker** - an autonomous execution agent inspired by Cline's "Act Mode" that executes structured plans generated by the PlanAgentWorker. Named after the Greek hero condemned to push a boulder uphill eternally, Sisyphus processes plans step-by-step, executing actions (file modifications, tool calls, tests), evaluating completion, and tracking changes. Unlike Cline's synchronous approval model, Sisyphus operates autonomously but creates detailed execution logs, visual diffs, and Git checkpoints for review and rollback.

## Goals

- Execute ExecutionPlan objects step-by-step with full autonomy
- Use LLM to determine actions needed for each step
- Execute tools (WriteFileTool, BashTool, etc.) to implement steps
- Evaluate step completion after each action sequence
- Generate visual diffs before applying changes
- Create Git checkpoints at milestone boundaries with rollback capability
- Stream real-time progress via SSE
- Generate detailed execution logs
- Handle errors gracefully with intelligent recovery
- Follow our OOP patterns and state machine architecture

## Prompt Architecture Overview

Sisyphus uses **7 distinct prompt classes** to guide execution:

1. **SisyphusSystemPrompt** - Master system prompt defining agent identity and capabilities
2. **ContextAssemblyPrompt** - Determines what codebase context is needed for a step
3. **StepPlanningPrompt** - Plans the sequence of tool calls to accomplish a step
4. **ToolValidationPrompt** - Validates tool parameters before execution
5. **StepExecutionPrompt** - Executes the planned tool calls with enhanced examples
6. **StepEvaluationPrompt** - Evaluates whether step objectives were met
7. **ErrorRecoveryPrompt** - Diagnoses failures and suggests recovery strategies

### 1.2 - Create StepExecutionWorkflow

**Intent**: Create the workflow responsible for executing a single plan step. This workflow determines what actions to take, executes tools, and records results.

**Details**:

- States: pending → assembling_context → planning → validating → executing → recording → complete/failed
- Accept parameters: step (PlanStep), path, owner_id, parent_memory, context, system_prompt
- Initialize workflow memory (WorkflowMemoryStore)
- **Step 1: Context Assembly**
  - Use ContextAssemblyPrompt to determine needed context
  - Gather files, patterns, directory structures
  - Store assembled context in workflow memory
- **Step 2: Planning**
  - Use StepPlanningPrompt to plan tool call sequence
  - Parse planned tool calls with rationales
- **Step 3: Validation**
  - Use ToolValidationPrompt for each planned tool call
  - Check for warnings/errors before execution

- **Step 4: Execution**
  - Use enhanced StepExecutionPrompt with full context
  - Execute tools via ToolCallService
  - Record each tool execution and result
  - Generate diffs for file changes (via DiffGenerationService)
- **Step 5: Recording**
  - Build StepResult object with: actions_taken, files_changed, tool_outputs, diffs, success/failure
  - Record execution decisions to memory
- Handle errors: catch tool failures, record errors, mark workflow failed

### 5.2 - Implement Step Execution Loop with Full Pipeline

**Intent**: Implement the complete step execution pipeline: context → plan → validate → execute → evaluate.

**Details**:
- Create execute_step method in SisyphusWorker:
  1. **Emit Progress**: "Executing step: {title}"
  2. **Record Decision**: Step start to memory
  3. **Check Approval** (if approval_mode != :autonomous):
     - Emit approval_required event with step details
     - Wait for approval (timeout 5 minutes)
     - If rejected, mark step skipped
  4. **Context Assembly**:
     - Use ContextAssemblyPrompt
     - Gather requested context
  5. **Planning**:
     - Use StepPlanningPrompt
     - Generate tool call sequence
  6. **Validation**:
     - Use ToolValidationPrompt for each tool call
     - Collect warnings/errors
     - If errors, attempt recovery or skip
  7. **Execution**:
     - Run StepExecutionWorkflow
     - Generate diffs for file changes
     - Store step_result
  8. **Evaluation**:
     - Run StepEvaluationWorkflow
     - Check if step objectives met
  9. **Retry Logic** (if evaluation failed):
     - If retries < max_retries:
       - Run ErrorRecoveryPrompt for diagnosis
       - Apply recovery actions
       - Retry execution
     - Else:
       - Mark step failed
       - Decide: continue or abort (based on config)
  10. **Record Completion**:
      - Update PlanStep status
      - Emit progress with result
      - Record to memory
- Track retry count per step (max 3 by default)
- Stream all sub-phases as progress events

- Named "Sisyphus" after the Greek hero condemned to eternally push a boulder uphill - a fitting metaphor for the perpetual nature of code execution and refinement
- Sisyphus can operate fully autonomously (unlike Cline) but provides approval mode for users who want control
- The 7-prompt architecture provides clear separation of concerns and better testability
- All prompts must be tested with real LLM calls (per project rules)
- Checkpoints enable safe exploration and easy rollback
- SSE streaming provides real-time visibility into execution
- Memory persistence enables learning across sessions
